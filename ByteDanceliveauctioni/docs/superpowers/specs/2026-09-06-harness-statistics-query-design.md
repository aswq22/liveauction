# DeepSeek Harness 竞拍统计查询设计

日期：2026-09-06
状态：设计已确认，进入实施计划阶段

## 1. 背景

当前竞拍商家后台已经能够展示今日工作台、拍品列表、订单列表和直播间快照；DeepSeek Harness 集成也已经具备登录、登录状态查询和创建团队成员能力。下一阶段需要让商家通过自然语言完成只读经营查询，而不要求用户记忆固定命令或工具参数。

本设计覆盖三个查询域：

1. 今日工作台全部看板数据。
2. 指定拍品的价格与竞拍状态。
3. 当前登录商家所有直播间正在拍卖的商品。

现有前端工作台通过分页拉取拍品与订单后在浏览器内聚合，最多读取约 500 条记录。该方式会重复业务口径，也可能在大数据量下产生不完整统计。因此采用“后端统一统计 + Harness 结构化查询工具”的架构。

## 2. 目标与非目标

### 2.1 目标

- 支持用户用多种口语、同义表达和上下文指代查询经营数据。
- 覆盖工作台核心指标、成交漏斗、趋势、Top 10、品类、订单风险和拍品明细。
- 支持按拍品 ID、完整标题或模糊关键词查询价格。
- 支持一次返回当前商家所有直播间正在拍卖的拍品。
- 以竞拍后端作为统计口径、权限和租户隔离的权威来源。
- 与现有 Harness 登录和动态账户切换流程协同。
- 返回可裁剪、可解释、带快照时间的结构化结果。
- 金额全链路使用整数分和明确币种。

### 2.2 非目标

- 不创建、修改、入队、开拍、落锤或取消拍品。
- 不查询指定买家正在参与的竞拍。
- 不把主账户 ID 暴露为模型可控制的查询参数。
- V1 不返回完整出价历史，只按需返回有限条近期出价。
- V1 不强制将现有 React 工作台迁移到新统计接口；稳定后再复用。
- 不允许模型直接读取数据库或自行拼接 SQL。

## 3. 已确认的产品规则

1. “今日工作台各看板”覆盖全部板块，而不仅是八个核心指标。
2. “正在拍卖的商品”指当前登录商家正在直播拍卖的拍品。
3. 商家存在多个直播间且用户未指定房间时，返回所有直播间的当前拍品。
4. “今日”固定按 `Asia/Shanghai` 自然日计算。
5. 查询采用后端统一聚合方案。
6. 查询工具只读，不需要二次确认。
7. 用户指定另一个主账户时，沿用登录检查、缺失密码追问和账户切换流程。
8. 工具不依赖固定句式；模型从自然语言中识别意图并填充结构化参数。

## 4. 方案选择

### 4.1 方案一：Harness 拉取原始数据并统计

Harness 调用现有拍品、订单和房间接口，再复制前端统计逻辑。优点是初始开发快；缺点是重复业务口径、受分页上限影响、难以保证跨查询一致性，也会把大量原始数据注入模型上下文。

### 4.2 方案二：后端统一统计，Harness 调用

后端新增主账户级工作台聚合接口，并复用或小幅增强现有拍品查询和房间快照接口。优点是统计口径唯一、能够在数据层完成完整聚合、权限边界清晰，未来网页与 Harness 可以共用；代价是需要调整后端协议、业务层和数据层。

### 4.3 方案三：给模型暴露通用查询接口

模型自行组合过滤和聚合条件。灵活性较高，但工具契约不稳定、权限面更大、结果难以审计，且模型容易对大量明细作出错误推断。

最终选择方案二。

## 5. 总体架构

```text
用户自然语言
    │
    ▼
DeepSeek Harness 意图理解与账户编排
    ├── auction_get_dashboard
    ├── auction_get_lot_price
    └── auction_get_live_lots
              │ Bearer Token
              ▼
竞拍 Go 后端
    ├── 工作台聚合接口（新增）
    ├── 拍品查询接口（复用/增强）
    └── 房间列表与快照接口（复用）
              │
              ▼
令牌所属主账户的订单、拍品、竞价与直播状态
```

### 5.1 后端职责

- 从认证令牌解析操作者和主账户，不接受客户端传入主账户 ID。
- 校验工作台、拍品和订单查看权限。
- 在数据层完整分页或直接聚合，不受浏览器端 500 条上限影响。
- 统一计算时间边界、金额、比率、趋势和风险口径。
- 对拍品、房间和直播快照强制应用租户范围。
- 返回稳定错误码、统计区间和快照时间。

### 5.2 Harness 职责

- 从自然语言选择工具并提取时间范围、板块、拍品或房间定位信息。
- 处理登录缺失、指定账户和账户切换。
- 对拍品与直播间名称进行受限搜索和消歧。
- 根据用户问题裁剪返回板块，避免无关数据挤占上下文。
- 将结构化数据组织为清晰、可追溯的自然语言回答。
- 不重算权威经营指标，不绕过后端权限判断。

## 6. 工作台聚合接口

新增主账户级接口：

```http
GET /api/admin/dashboard?range=today&timezone=Asia%2FShanghai&sections=summary,funnel,trend,topLots
Authorization: Bearer <access-token>
```

`range` 支持：

- `today`：Asia/Shanghai 当日 00:00 至当前快照时间。
- `live`：当前处于直播或竞拍中的场次范围。
- `7d`：含今日在内的最近 7 个自然日。
- `30d`：含今日在内的最近 30 个自然日。

`sections` 可选；省略表示返回全部板块。后端仍负责校验调用者是否具备读取相应数据的权限。

建议响应轮廓：

```json
{
  "range": {
    "type": "today",
    "timezone": "Asia/Shanghai",
    "startUnixMs": 0,
    "endUnixMs": 0
  },
  "snapshotAtUnixMs": 0,
  "currency": "CNY",
  "summary": {
    "gmvAmount": 0,
    "paidAmount": 0,
    "pendingAmount": 0,
    "orderCount": 0,
    "cancelledOrderCount": 0,
    "paymentRate": 0,
    "dealRate": 0,
    "participantCount": 0,
    "averageDealAmount": 0
  },
  "funnel": {},
  "paymentTrend": [],
  "topLots": [],
  "categoryPerformance": [],
  "orderRisks": {},
  "lotPerformance": [],
  "partialErrors": []
}
```

### 6.1 统计口径

- GMV：统计区间内已支付订单的实付金额总和。
- 已支付金额：已支付订单金额总和；V1 与 GMV 保持同一现有业务定义。
- 待支付金额：已成交并已生成订单、但尚未支付的订单金额。
- 订单数：区间内创建的有效订单数；取消订单单独返回，不混入有效订单数。
- 支付率：已支付订单数除以应支付订单数；分母为零时返回 0，并带有效计数供调用方解释。
- 成交率：已成交拍品数除以已经开拍的拍品数；分母为零时返回 0。
- 参拍人数：按主账户范围内的用户 ID 去重，不能把各拍品参与人数简单相加。
- 平均成交价：已支付金额除以已支付订单数，按整数分返回。
- 成交漏斗：已创建、已上架、已开拍、有出价、已成交和已支付各阶段数量。
- 支付趋势：`today` 按小时，`7d` 与 `30d` 按自然日聚合；`live` 按适合场次长度的固定桶聚合。
- 成交额 Top 10：按已支付成交额降序，金额相同使用稳定次序。
- 品类表现：按品类聚合成交额、成交数、开拍数和成交率。
- 订单风险：至少包括待支付、即将超时、已超时和支付异常。
- 拍品表现：返回当前能够可靠取得的浏览、参拍、出价、成交等指标；没有可靠数据的字段标记不可用，不使用推测值。

所有金额字段均以整数分表示，并在顶层返回 `currency: "CNY"`。格式化成人民币展示文本由 Harness 或前端负责。

### 6.2 一致性与完整性

- 尽量使用同一数据库读快照完成多表统计。
- 每次响应包含实际统计区间和 `snapshotAtUnixMs`。
- 单个非核心板块失败时，通过 `partialErrors` 返回失败板块与安全错误码，同时保留已成功板块。
- 核心汇总无法读取时整次请求失败，不能返回看似有效的零值。

## 7. Harness 工具契约

### 7.1 `auction_get_dashboard`

输入：

```json
{
  "range": "today",
  "sections": ["summary", "funnel", "trend", "topLots"]
}
```

- `range` 默认为 `today`。
- `sections` 省略时查询全部看板；用户只问单项时只请求相关板块。
- 返回权威结构化统计、范围、币种、快照时间和部分错误。
- “今天咋样”“看看今日工作台”“最近一周成交额最高的拍品”等不同表达映射到同一工具和不同参数。

### 7.2 `auction_get_lot_price`

输入：

```json
{
  "lotId": "",
  "keyword": "茅台",
  "roomId": "",
  "includeHistory": false
}
```

约束与解析顺序：

1. `lotId` 与 `keyword` 至少提供一个，准确 ID 优先。
2. 标题完全匹配时直接选择。
3. 模糊搜索只有一个结果时直接返回。
4. 多个结果时返回最多 5 个安全候选，不猜测目标。
5. 无结果时返回搜索条件和可操作提示。
6. `roomId` 仅用于当前主账户内缩小范围，不改变租户边界。

结果包含拍品 ID、标题、房间、状态、起拍价、当前价、最低加价、封顶价、成交价、领先者昵称、出价次数和更新时间。默认不返回用户内部 ID；V1 默认不返回完整历史。

### 7.3 `auction_get_live_lots`

输入：

```json
{
  "roomId": "",
  "includeRecentBids": false
}
```

- 未指定直播间时读取当前主账户的全部直播间。
- 指定房间名称时先在租户内解析；重名时返回候选并追问。
- 每个房间最多返回一个当前权威直播拍品，以及下一件排队拍品摘要。
- 默认不取近期出价；用户询问“最近谁出价”时才启用有限条近期出价。
- 无直播拍品是正常业务结果 `NO_LIVE_LOT`，不是系统异常。

每项结果包含直播间名称与 ID、拍品标题与 ID、起拍价、当前价、最低加价、领先者昵称、参拍人数、出价次数、开始时间、预计结束时间、剩余时间、下一件拍品摘要和数据快照时间。

## 8. 自然语言与账户编排

三个查询工具只消费当前认证会话，不接收账号、密码或主账户 ID。外层编排使用统一流程：

```text
用户查询
  │
  ├── 未指定主账户
  │     ├── 已登录：使用当前会话
  │     └── 未登录：追问账号；缺密码时继续追问密码
  │
  └── 明确指定主账户
        ├── 当前会话匹配：直接查询
        └── 不匹配：尝试安全凭据或追问该账号密码，登录切换后查询
```

自然语言理解由模型承担，业务安全由工具与后端承担。提示和工具描述需覆盖：

- 同义表达：“成交额”“卖了多少钱”“GMV”。
- 口语省略：“今天咋样”“付款情况呢”。
- 时间表达：“今天”“最近一周”“近 30 天”。
- 上下文指代：“刚才那件”“这个直播间”；只有上下文唯一时才能解析。
- 指定账户：“换到张三的主账号看看今天成交情况”。
- 多直播间：“所有场子现在分别拍什么”。

无法唯一解析拍品、房间、时间或账户时，必须返回候选或追问，不允许静默猜测。

## 9. 权限与安全边界

- 后端从令牌解析主账户，任何工具参数都不能覆盖该范围。
- 工作台全量查询需要现有 `realtime.view`、`lot.view_admin` 和 `order.manage` 权限；缺失任一权限返回明确错误。
- 拍品价格与房间查询按实际读取内容检查 `lot.view_admin` 和 `realtime.view`。
- 每次请求重新校验权限，不能仅依赖登录时缓存的角色。
- 拍品和房间搜索始终限定在当前主账户。
- 默认隐藏用户 ID、手机号、地址、令牌、密码和其他个人敏感信息。
- 密码仅传给登录工具，不传给查询工具，不出现在日志和查询结果。
- 日志仅记录工具名称、耗时、结果数量、板块和错误码。
- 限制关键词长度、候选数量、近期出价数量和响应明细数量。
- 自然语言中的账号、标题和房间名始终作为数据处理，不能影响工具指令或权限规则。

## 10. 错误模型

稳定错误码至少包括：

- `AUTH_REQUIRED`：缺少登录会话，进入账号与密码追问流程。
- `ACCOUNT_MISMATCH`：当前会话与明确指定账号不一致，进入切换流程。
- `PERMISSION_DENIED`：当前操作者没有所需权限。
- `ROOM_AMBIGUOUS`：房间名称匹配多个候选。
- `LOT_AMBIGUOUS`：拍品定位匹配多个候选。
- `LOT_NOT_FOUND`：当前主账户内未找到拍品。
- `NO_LIVE_LOT`：目标范围当前没有直播拍品。
- `BACKEND_UNAVAILABLE`：后端不可达或超时。
- `DATA_INCOMPLETE`：部分统计板块失败。
- `VALIDATION_ERROR`：参数或范围不合法。

错误响应需包含安全、可行动的信息，但不能透传数据库错误、内部堆栈、令牌或供应商细节。

## 11. 代码组织

后端预计涉及：

```text
live-auction-bid-backend/
├── api/auction/service/v1/auction.proto
└── app/auction/service/internal/
    ├── service/auction.go
    ├── biz/auction/
    └── data/
```

Harness 集成拆分为：

```text
integrations/deepseek-harness/
├── src/
│   ├── auth.mjs
│   ├── auction-client.mjs
│   ├── query-tools.mjs
│   ├── schemas.mjs
│   └── plugin.mjs
└── test/
```

- `auth.mjs` 只管理登录与会话状态。
- `auction-client.mjs` 封装竞拍 HTTP API、认证头、超时和安全错误映射。
- `query-tools.mjs` 处理参数校验、房间/拍品消歧和结果裁剪。
- `schemas.mjs` 集中维护工具输入输出 Schema。
- `plugin.mjs` 仅负责 Cordis/Harness 插件注册与组装。

## 12. 测试策略

### 12.1 后端

- Asia/Shanghai 今日边界、跨午夜和夏令时无影响场景。
- 无订单、无拍品、零分母与大数据量。
- 已支付、待支付、取消、即将超时、已超时和支付异常口径。
- 同一用户参与多个拍品时正确去重。
- 趋势桶、Top 10 稳定排序、品类和漏斗统计。
- 多直播间同时直播以及无直播拍品。
- 主账户隔离和各权限不足。
- 部分板块失败时保留成功结果。

### 12.2 Harness

- 未登录、已登录、指定相同账户和切换账户。
- 按 ID、完整标题和模糊关键词查价。
- 拍品或直播间重名时返回有限候选。
- 全部直播间、单一直播间和无直播拍品。
- 后端超时、不可用、非法响应和部分失败。
- 结果大小限制与敏感字段裁剪。
- 密码和令牌不出现在输出与日志中。

### 12.3 自然语言验收

测试集必须包含多种表达而不是固定模板，例如：

- “今天咋样？”
- “付款情况呢？”
- “今天支付率和待付款金额是多少？”
- “最近七天成交额最高的拍品有哪些？”
- “青花瓷现在多少钱？”
- “刚才那件现在多少钱？”
- “所有场子现在分别拍什么？”
- “目前谁领先？”
- “换到张三的主账号，看看今天成交情况。”

上下文指代只有在会话内存在唯一候选时才算通过；否则必须追问。

## 13. 分阶段实施

### Phase 1：后端统计契约

- 为工作台请求、响应和错误补充协议定义。
- 先编写时间、金额、漏斗、风险和租户隔离失败测试。
- 实现业务聚合与数据层查询。
- 暴露 HTTP 接口并验证生成代码。

### Phase 2：Harness 查询基础设施

- 从现有认证类中抽出通用 API 客户端。
- 增加 Schema、超时、安全错误和结果裁剪。
- 保持已有登录与团队成员工具兼容。

### Phase 3：三个查询工具

- 实现工作台分板块查询。
- 实现拍品 ID、标题、模糊搜索和消歧。
- 实现所有直播间当前拍品查询。

### Phase 4：自然语言与运行时验证

- 完善工具描述、账户切换和追问行为。
- 使用单元测试、后端集成测试和 Cordis 运行时烟雾测试验证。
- 使用受控真实 DeepSeek 提示词覆盖口语、同义词、指代和歧义场景。

## 14. 验收标准

1. 用户能够用自然语言查询工作台全部板块或其中任一板块。
2. “今日”始终按 Asia/Shanghai 计算，并在结果中返回实际区间和快照时间。
3. 工作台统计不受前端分页上限影响，参拍人数按用户去重。
4. 用户能够按 ID、标题或关键词查询拍品价格；多匹配时系统不猜测。
5. 未指定直播间时返回当前商家所有直播间的当前拍品。
6. 多个直播间或拍品重名时返回候选并继续追问。
7. 未登录时追问所需凭据；明确指定不同主账户时能够安全切换。
