# AI 竞拍 Agent 对话补全与审批入队设计

日期：2026-08-28
状态：设计已书面确认，进入实施计划阶段

## 1. 背景

当前 AI 运营 Agent 能查询商家真实库存并生成只读竞拍方案，但不能把方案安全地转化为拍品队列，也不能处理“创建一个新拍品”这类信息不完整的自然语言请求。现有人工添加拍品流程需要填写资料、上传图片、设置竞拍规则、创建草稿并入队，操作步骤较多。

本设计在现有 Go 后端、Python Agent Service 和 React 管理端之上增加一个可恢复、可追问、可编辑、可审批和可审计的闭环：

```text
自然语言需求
→ Agent 查询库存或解析新拍品
→ 最少必要追问与图片上传
→ 生成可编辑确认快照
→ 用户批量选择并确认
→ Go 在单个事务中创建新拍品并追加队列
→ 用户在队列页手动开拍
```

本文件细化并取代 `2026-08-25-live-auction-agent-design.md` 中“审批执行闭环”的写入边界。Python Agent 不获得创建拍品、修改拍品或入队工具；所有业务写入由 Go 审批执行器完成。

## 2. 目标与非目标

### 2.1 目标

- 从现有库存生成竞拍方案，用户确认后批量追加到拍品队列。
- 从自然语言创建一个或多个新拍品候选项。
- 对不能安全推断的必填信息进行对话式追问。
- 允许用户为每个新拍品上传真实主图。
- 自动生成介绍、分类、标签及竞拍规则建议，并允许用户编辑。
- 对话、草稿、上传状态和确认结果可在刷新或重新登录后恢复。
- 批量确认默认全选，允许取消勾选和调整批次内部顺序。
- 批量创建与入队必须具备数据库原子性、幂等性和审计能力。
- 入队后仍由用户在现有队列页手动开拍。

### 2.2 非目标

- 不自动开拍、落锤、取消拍品或处理资金。
- 不允许 Python Agent 或模型直接修改业务数据库。
- V1 不生成 AI 商品图片，只允许上传真实商品图片。
- 不重排、插队或修改当前已有队列顺序。
- 不在最终确认前创建真实拍品记录。
- 不实现语音、多模态商品识别或通用文件管理。

## 3. 已确认的产品规则

1. 批量确认默认选中全部拍品，用户可以取消勾选部分拍品。
2. 最终确认前只保存 Agent 会话草稿，不创建真实拍品。
3. 使用“最少追问 + 可编辑默认值”模式。
4. 新拍品必须上传真实主图，V1 不提供 AI 商品图生成。
5. Agent 会话必须持久化并支持恢复。
6. 批量确认采用全有或全无的原子事务。
7. 新批次整体追加到当前队尾，不改变已有拍品顺序。
8. 自然语言中的“价格 10000”默认表示起拍价人民币 10,000 元；界面按元展示，后端按分存储。
9. 拍品名称、起拍价、竞拍时长和主图必须由用户明确提供；缺失时 Agent 必须追问。
10. 分类、标签、介绍、库存、最低加价、反狙击规则、保证金和未明确的封顶价策略可以由模型或系统提供可编辑建议。

## 4. 总体架构

```text
React Agent Console
  ├── 可恢复对话
  ├── 候选拍品草稿
  ├── 图片上传
  └── 批量确认页
          │ HTTP + SSE
          ▼
Go Auction Backend
  ├── Agent Session Service
  ├── Turn / Run Gateway
  ├── Draft Validator
  ├── Approval Snapshot Service
  ├── Atomic Proposal Applier
  └── Audit + Transactional Outbox
          │ gRPC
          ▼
Python Agent Service
  ├── Intent Router
  ├── Lot Draft Skill
  ├── Existing Inventory Planning Skill
  ├── Structured Question Generator
  └── Read-only Tool Registry
```

### 4.1 React 职责

- 展示并恢复对话、Run 轨迹和候选拍品。
- 为指定候选拍品上传主图并展示上传状态。
- 提供结构化字段编辑，不要求用户只能通过自然语言修改。
- 展示字段来源：用户输入、AI 建议、系统默认或已有拍品。
- 提供默认全选、取消勾选和批次内部排序。
- 提交带会话版本、快照版本和幂等键的确认命令。

### 4.2 Go 职责

- 作为会话、确认快照、审批记录和业务拍品的权威所有者。
- 校验认证、RBAC、主账户、直播间、已有拍品和图片资产归属。
- 对 Python 返回的结构化结果做确定性 Schema 与业务校验。
- 合并候选拍品字段并维护乐观锁版本。
- 生成不可变确认快照。
- 在一个 MySQL 事务中创建新拍品、关联图片、分配队列位置、写审批审计及 Outbox。
- 将安全事件和错误通过 HTTP/SSE 返回前端。

### 4.3 Python 职责

- 识别请求是现有库存排品、新拍品创建或两者混合。
- 查询商家自有库存和历史数据等只读上下文。
- 提取用户明确字段，生成非关键字段建议。
- 判断哪些用户必填信息仍然缺失并生成简洁追问。
- 返回严格结构化的候选补丁、问题、风险和就绪状态。
- 永远不执行创建、修改、入队或开拍操作。

## 5. 会话与状态模型

现有 `agent_runs` 继续表示一次异步模型执行。新增更上层的持久化 `agent_sessions`；一个会话可以包含多条消息、多个 Run、多个候选拍品和多个确认快照。

### 5.1 会话状态

```text
COLLECTING_INPUT
      │ 信息完整
      ▼
READY_FOR_REVIEW
      │ 用户确认
      ▼
APPLYING
      │ 原子事务成功
      ▼
APPLIED

校验、版本或执行冲突 → NEEDS_REVISION
用户主动放弃          → CANCELLED
```

信息缺失是正常会话状态，不是 Run 失败。模型或传输故障只使当前 Turn 失败，不能丢失已保存的消息、图片和候选草稿。

### 5.2 建议数据表

#### `agent_sessions`

- `id`
- `tenant_id`
- `operator_id`
- `room_id`
- `status`
- `version`
- `conversation_summary`
- `active_snapshot_version`
- 创建、更新时间

#### `agent_session_messages`

- `session_id`
- `seq`
- `role`
- `content`
- `run_id`
- 创建时间

#### `agent_draft_candidates`

- `id`
- `session_id`
- `source_type`：`EXISTING` 或 `NEW`
- `existing_lot_id`
- `position`
- `selected_by_default`
- `draft_json`
- `field_sources_json`
- `validation_json`
- `version`

`draft_json` 只保存候选资料，不是业务 `lots` 表记录。`field_sources_json` 记录每个字段来自用户、AI、系统默认或已有数据。

#### `agent_approval_snapshots`

- `session_id`
- `snapshot_version`
- `snapshot_json`
- `content_hash`
- `created_by`
- 创建时间

快照不可原地修改。任何消息、字段编辑、图片变化、勾选或排序变化都会生成新版本，使旧确认版本失效。

#### `agent_proposal_executions`

- `id`
- `session_id`
- `snapshot_version`
- `idempotency_key`
- `operator_id`
- `status`
- `selected_candidate_ids_json`
- `created_lot_ids_json`
- `queue_positions_json`
- `error_code`
- 创建、完成时间

`session_id + snapshot_version + idempotency_key` 建立唯一约束。

## 6. 意图与候选拍品模型

候选项统一支持三种会话结果：

- 仅现有拍品：从 `inventory.query` 的真实拍品中选择和排序。
- 仅新拍品：从用户描述构造尚未落库的候选草稿。
- 混合方案：同一确认快照同时包含 `EXISTING` 与 `NEW` 候选项。

已有拍品候选项必须保存拍品 ID、读取时版本和关键字段摘要。确认时 Go 必须重新读取并校验版本、归属、状态和是否已经入队，不能只信任快照。

新拍品候选项至少包含：

- 名称
- 起拍价
- 竞拍时长
- 主图资产 ID 与稳定 URL
- 分类、标签和介绍
- 最低加价
- 封顶价
- 库存
- 反狙击窗口、延长秒数和最大次数
- 保证金、估价、售后和讲解卡等可选内容

## 7. 最少追问与默认值

### 7.1 必须由用户明确提供

- 拍品名称
- 起拍价
- 竞拍时长
- 主图上传

如果字段缺失、含义冲突或无法判断属于哪个拍品，Agent 返回 `NEEDS_INPUT`。模型不能为这些字段静默猜值并进入确认页。

### 7.2 可生成或采用系统默认

- 当前直播间：当前主账户的默认房间。
- 分类、标签、介绍：模型建议。
- 库存：默认 1。
- 最低加价：根据起拍价档位的确定性规则给出建议。
- 反狙击：窗口 10 秒、每次延长 15 秒、最多 5 次。
- 保证金：默认 0。
- 封顶价：用户未提到时不启用。
- 币种：CNY。

这些字段必须在确认页可编辑，并显示来源。Go 对范围、币种、金额、图片 URL 和规则关系再次验证。

### 7.3 示例

用户输入：

> 我要拍卖名为海洋之心的宝石，价格10000，时长50分钟，封顶价格100000

系统解析：

- 名称：海洋之心
- 起拍价：CNY 10,000 元
- 时长：3,000 秒
- 封顶价：CNY 100,000 元
- 分类建议：珠宝彩宝
- 库存默认：1
- 介绍、标签、最低加价和反狙击规则：生成建议
- 缺失项：真实主图

Agent 只追问主图，并在消息中提供绑定到该候选拍品的上传按钮。若用户没有提供起拍价或竞拍时长，则对应字段也必须出现在追问中。

## 8. Agent 每轮协议

每条用户消息或结构化字段编辑都可以触发一个归属于会话的异步 Agent Run。现有 SSE、事件序号、断线续传和安全错误边界继续复用。

Run 类型：

- `SESSION_PLAN`：从已有库存生成排品方案。
- `LOT_DRAFT_ASSIST`：解析新拍品、补全建议并生成追问。

Go 传给 Python 的输入包括：

- 会话 ID、会话版本和 Run 安全上下文。
- 用户本轮消息。
- 当前结构化候选草稿。
- 最近必要对话及压缩摘要。
- 当前房间和允许读取的账户上下文。
- 已上传图片的资产引用；不传原始文件字节。

Python 返回严格结构化结果：

```text
assistant_message
candidate_patches[]
required_inputs[]
review_readiness
warnings[]
```

`required_inputs` 使用稳定类型，例如：

- `TITLE`
- `START_PRICE`
- `DURATION`
- `MAIN_IMAGE`
- `AMBIGUOUS_CANDIDATE`

模型返回的候选补丁不能直接覆盖用户明确填写的字段。冲突内容转为建议或警告，由用户选择是否采用。Go 合并前必须验证候选 ID、字段来源和 Schema。

## 9. 前端交互

Agent 控制台采用“可恢复对话 + 候选草稿面板”。

### 9.1 对话区

- 支持自然语言输入和历史消息恢复。
- 显示理解需求、查询库存、生成建议和等待补充等 SSE 状态。
- 对起拍价和时长提供文字回复及内嵌数字输入。
- 对主图问题提供“选择图片上传”，并明确显示对应候选拍品。
- 模型失败时保留草稿并允许重试当前 Turn。

### 9.2 草稿区

- 每个候选项独立显示字段、来源、缺失项和校验错误。
- 用户可以直接编辑字段，编辑后会话版本递增并重新校验。
- 上传图片使用现有 `/api/uploads/images`，资产在确认前保持未绑定业务拍品状态。
- 删除或替换图片复用现有资产删除和孤儿清理机制。

### 9.3 确认页

- 全部候选项默认勾选。
- 允许取消勾选，但至少保留一项才能确认。
- 允许调整本批次内部顺序。
- 勾选或排序变化会生成新的不可变确认快照；执行请求必须与该快照完全一致。
- 明确区分已有拍品与待创建新拍品。
- 展示最终价格、时长、图片、规则、字段来源和风险。
- 确认按钮显示“确认并加入队列（N 件）”。
- 成功后跳转现有拍品队列；用户手动点击“开始竞拍”。

## 10. 审批执行器

Go 新增领域命令：

```text
ApplyAgentProposal(
  session_id,
  snapshot_version,
  selected_candidate_ids,
  ordered_candidate_ids,
  idempotency_key
)
```

### 10.1 事务步骤

在一个 MySQL 事务中：

1. 校验会话、快照版本、内容哈希、操作者和主账户权限。
2. 锁定直播间队列计数器和涉及的已有拍品。
3. 校验全部选中拍品的归属、版本、状态和可入队性。
4. 校验新拍品名称、起拍价、时长、主图、竞拍规则和图片资产归属。
5. 为新候选项创建真实 `lots` 记录。
6. 关联主图、轮播图和讲解卡资产。
7. 从当前队尾开始为全部选中拍品分配连续位置，保持确认顺序。
8. 写入审批执行记录、拍品领域事件和 Transactional Outbox。
9. 更新会话为 `APPLIED` 并提交事务。

事务提交后由现有 Outbox/广播链路发布队列变化。任何一步失败都会回滚，不留下新拍品、半截队列、已占用位置或部分审批结果。

### 10.2 并发与幂等

- 锁定房间队列计数器，避免两个批次分配相同位置。
- 使用现有队列位置唯一约束作为最终防线。
- 执行请求的选择集合和顺序必须与指定快照完全一致，否则按过期快照拒绝。
- 重复确认使用相同幂等键时返回同一执行结果。
- 相同会话的不同快照版本不能复用执行结果。
- 快照过期、已有拍品被修改、取消或入队时返回稳定冲突错误，会话进入 `NEEDS_REVISION`。
- 不静默覆盖、不自动重排已有队列，也不对已变化拍品做猜测性修复。

```text
POST   /api/admin/agent/sessions/{session_id}/apply
POST   /api/admin/agent/sessions/{session_id}/cancel
```

图片上传底层继续复用现有上传 API 和资产表；会话图片接口负责候选项绑定语义，不重复实现存储服务。

gRPC 在现有兼容规则下增加 Run 类型和结构化 Turn 输入/结果字段。字段编号只追加，不复用；旧的只读规划 Run 保持兼容。

## 12. 错误处理

稳定业务错误至少包括：

- `AGENT_SESSION_NOT_FOUND`
- `AGENT_SESSION_VERSION_CONFLICT`
- `AGENT_REQUIRED_INPUT_MISSING`
- `AGENT_IMAGE_ASSET_INVALID`
- `AGENT_REVIEW_SNAPSHOT_STALE`
- `AGENT_CANDIDATE_CHANGED`
- `AGENT_BATCH_APPLY_FAILED`
- `AGENT_BATCH_ALREADY_APPLIED`

浏览器只接收安全消息。模型供应商、密钥、Prompt、内部存储路径和数据库错误不能透传。

恢复策略：

- 模型或网络失败：保留会话并重试当前 Turn。
- 图片上传失败：只重试该图片。
- 信息缺失：保持 `COLLECTING_INPUT`，不是失败。
- 快照或候选项冲突：转 `NEEDS_REVISION` 并重新生成确认快照。
- 事务失败：整批回滚并保留可编辑会话。
- 已成功请求重放：返回已有执行结果。

## 13. 安全与审计

- Python Tool Registry 继续保持只读闭集。
- 模型输出中的 `approved`、`confirmed` 或类似字段不具有授权意义。
- Go 在每次会话、上传、快照和执行请求上重新验证当前用户身份与主账户权限。
- 图片资产必须属于当前操作者或主账户，并匹配候选会话及房间。
- 确认快照保存操作者、字段值、字段来源、选择集合、顺序、版本和内容哈希。
- 执行记录保存创建的拍品 ID、最终队列位置、事务结果和错误码。
- 日志和 Trace 默认不记录完整商品介绍、原始对话、图片内容或模型密钥。

## 14. 可观测性

核心 Trace：

```text
session.message
→ agent.run
→ agent.model
→ agent.read_tool
→ session.merge
→ snapshot.create
→ proposal.apply.transaction
→ outbox.publish
```

核心指标：

- 从首条消息到 `READY_FOR_REVIEW` 的耗时和对话轮数。
- 必填字段首次提取准确率与追问率。
- AI 建议字段被用户修改的比例。
- 图片上传成功率和孤儿资产清理量。
- 确认转化率、快照过期率和批量执行成功率。
- 原子事务回滚、幂等命中和并发冲突次数。
- 从确认到队列可见的端到端延迟。

## 15. 测试策略

### 15.1 Python

- 现有库存、新拍品和混合意图路由。
- 名称、起拍价、时长和主图缺失时的必填追问。
- 金额按人民币元理解并结构化输出。
- 分类、介绍、最低加价和反狙击建议。
- 用户明确字段不被模型补丁静默覆盖。
- 模型输出 Schema、Token 预算、停止条件和错误安全。
- Agent 无法申请或调用写工具。

### 15.2 Go

- 会话和消息的租户隔离、恢复和乐观锁。
- 候选补丁 Schema、字段来源和确定性业务校验。
- 上传资产归属、替换、删除和孤儿清理。
- 确认快照不可变及旧版本失效。
- 批量事务成功时连续追加队列。
- 任意候选项失败时零拍品、零队列变化、零部分审批。
- 并发确认、重复点击、幂等重放和队列唯一约束。
- Outbox 与审批记录和业务变更处于同一事务。

### 15.3 React

- 刷新后恢复消息、候选项、上传状态和 Run 轨迹。
- 按候选拍品上传和替换主图。
- 编辑 AI 建议字段后正确失效旧快照。
- 确认页默认全选、取消勾选、内部排序和至少选择一项校验。
- 重复点击保护、版本冲突和安全错误提示。
- 成功后跳转队列且不自动调用 StartLot。

### 15.4 端到端

1. 从已有库存生成方案，取消部分勾选后按方案顺序追加队尾。
2. 输入“海洋之心”示例，Agent 只追问主图，上传后确认并入队。
3. 缺少起拍价或时长时必须追问，不能直接进入确认。
4. 批次中任一项无效时验证 MySQL 没有产生拍品或队列变化。
5. 两个会话并发确认时队列位置唯一且各批次内部连续。
6. 重放同一确认请求不会生成重复拍品。
7. 入队后只能由用户在队列页手动开拍。
8. 真实 DeepSeek 只作为受控烟雾测试；主要回归使用 FakeModel 和固定 Eval 数据。

## 16. 分阶段实施

### Phase 1：持久对话与结构化草稿

- 会话、消息、候选项和 Run 关联表。
- 新拍品意图解析与必填追问。
- 会话恢复和候选草稿编辑。

### Phase 2：图片与确认快照

- 候选项图片上传绑定。
- 字段来源和校验展示。
- 默认全选、取消勾选、内部排序和不可变确认快照。

### Phase 3：Go 原子审批执行器

- 批量事务、连续队列位置、资产关联、审批审计和 Outbox。
- 幂等、并发冲突、快照失效和整批回滚。

### Phase 4：评测与作品集完善

- 固定自然语言 Eval 数据集。
- 真实 DeepSeek 烟雾测试与成本指标。
- Trace、监控面板、架构图和演示脚本。

## 17. 验收标准

1. 用户能在同一可恢复会话中生成已有库存方案或创建新拍品候选。
2. 名称、起拍价、竞拍时长和主图缺失时，Agent 必须追问。
3. 用户可以上传真实主图并编辑所有 AI 建议字段。
4. 确认页默认全选，支持取消勾选和调整本批次顺序。
5. 最终确认前 `lots` 表不存在对应新拍品。
6. 确认后全部选中拍品在一个事务中创建或入队，并连续追加队尾。
7. 任意校验或写入失败时整批回滚。
8. 重复确认不创建重复拍品，过期确认不会覆盖新状态。
9. Python Agent 全程没有写工具；所有写入由 Go 审批执行器完成。
10. 入队后不会自动开拍，用户可在现有队列页手动开始竞拍。
11. 会话、审批、最终字段来源和队列位置可以审计。
12. Agent 服务或模型失败不影响现有竞价、订单和直播主链路。
