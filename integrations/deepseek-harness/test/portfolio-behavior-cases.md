# 多账号经营分析行为验收

## 自动化基线

实现前的插件只有六个 Tool、一个会话级 `AuctionAuth`，没有 Skill 服务注入或多账号组合 Tool。面对多账号请求，运行时不存在一次完成隔离认证与确定性汇总的能力；若模型尝试完成，只能反复切换单账号登录态并在上下文中自行计算。这是本 Skill 要纠正的结构性基线。

当前自动化验证覆盖：

| 场景 | 可观察结果 |
| --- | --- |
| 三账号 30 日汇总 | Tool 清单提供一次性组合调用，不依赖当前会话登录态 |
| 多账号支付率 | 合并分子、分母后重算，不平均账号百分比 |
| 一个账号认证失败 | 返回 `PARTIAL` 和 `included/requested`，其余账号继续汇总 |
| 同一租户使用两个登录名 | 按认证后的 `mainAccountId` 去重并返回 `DUPLICATE_ACCOUNT` |
| 单账号 GMV | 普通 `auction_get_dashboard` 保持可用，Skill 描述明确排除单账号请求 |
| 异常拍品诊断 | `LOT_NO_CONVERSION` 来自确定性规则，其他原因只能作为分析推断 |
| 组合查询期间已有登录 | 临时账号分别使用自己的 Token，调用后原登录账号不变 |
| 调用取消或失败 | 所有已创建的临时认证对象都执行清理 |

`npm test` 验证参数、聚合、失败降级、清理、注册和回归；`runtime-smoke.mjs` 使用真实 Cordis、ToolRuntime、SkillRegistry 和本地 HTTP fixture 验证 Skill 可发现、正文可加载、组合 Tool 可执行及输出 Schema 兼容。

## 配置模型后的人工验收

只使用受控测试账号，不在本文档或录屏中保存真实密码。

| 编号 | 用户意图 | 通过标准 |
| --- | --- | --- |
| P1 | 汇总三个店最近 30 天总体表现 | 加载 `analyzing-auction-portfolio`，只调用一次组合 Tool |
| P2 | 比较三个店的支付率 | 展示合并分子、分母和加权比率，不对百分比求平均 |
| P3 | 其中一个账号密码错误 | 开头披露 `included/requested`，不把结果称为全部账号 |
| P4 | 只查店铺 A 今天 GMV | 使用单账号 Dashboard Tool，不进入组合流程 |
| P5 | 找出异常商品并给建议 | 系统风险只引用 `riskFlags`，原因解释标为推断，建议与证据对应 |
| P6 | 两个凭据实际属于同一商家 | 只统计一次并说明重复账号未纳入 |
| P7 | 所有账号均登录失败 | 返回失败范围，不输出零成交额或经营建议 |

人工记录应保存 Tool 名称、Tool 状态、覆盖率表达和事实/推断边界，不保存请求参数中的密码。当前环境未配置可用于自动评测的真实模型，因此这些自然语言案例不伪装成已自动通过；它们是部署后必须执行的模型行为验收。
